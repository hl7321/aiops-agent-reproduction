## Context

动机与实测证据见 `proposal.md`。这里是决定实现方式的现状与约束。

**现状数据流**（`apps/backend/src/super_ai/aiops/`）：

```
tool_policy.build_aiops_tool_registry()
  └─ 真实发现 ∩ 只读判定 → registry + 模型可见目录（含 DescribeLogContext）

planning.validate_plan()
  └─ requiresTemporalContext 为真 → 必须恰好有一个 DescribeLogContext 步骤

runtime.executor
  └─ 上下文步骤分支：从最近一次 log_hit 取 Time/PkgId/PkgLogId
     hit.has_context_locator 为假 → 抛"缺少已验证 SearchLog 定位命中"

runtime.replanner
  └─ requires_temporal_context = 计划里是否存在上下文步骤
```

**关键事实**：`hit.has_context_locator` 在当前数据源上**恒为假**（命中的 `PkgId`/`PkgLogId`
都是空串）。因此这条分支永远走不通，而 `requires_temporal_context` 又会被它激活，
把已经拿到的多条日志命中判成"时序证据不足"。

**实测反证**：`incident_id:"java-ecom-001-..."` 一次检索就返回了同一链路的 4 行日志
（序号 1→4，覆盖基线/症状/异常/恢复）。也就是说，**要证明的"前后过程"本来就在第一次检索结果里**。

**约束**：退役判定必须可追溯、可测试；不得把"没登记语义"和"数据源不可用"混为一谈；
不改证据充分性判据本身；不动 Executor 不得自行加步骤/换工具的可控性。

## Goals / Non-Goals

**Goals:**

- 让 Planner 不再规划一个在当前数据源上不可能成功的工具。
- 让"声明时序需求"不再必然导致计划非法。
- 让时序证据判定只在"计划确实包含上下文步骤"时生效，不再被虚假激活。

**Non-Goals:**

- 不换上传路径产出定位字段，不改 `DescribeLogContext` 的必填参数定义。
- 不改证据充分性判据、attempt 上限与其它失败分类。
- 不实现"第二次日志检索取上下文"（作为备选写进文档）。
- 不处理同类但独立的"指标类工具在日志主题上不可用"（见 proposal Impact）。

## Decisions

### D1 · 用"数据源可用性"而不是"是否登记"来表达退役

**选择**：在语义登记表上增加一条**数据源不可用**的标记（含判定依据），`DescribeLogContext`
据此从 registry 与模型可见目录中同时移除。

**备选：把它从 policy 里删掉。** 否掉——那会退化成"未登记语义"路径（可执行、产物落中间产物），
工具依然可被规划，只是产物没有语义；这与退役的意图相反，也丢掉了判定依据。

**备选：只在提示词里告诉模型"别用它"。** 否掉——靠提示词约束不可靠，且目录里仍然存在该工具，
模型仍可能规划它。

### D2 · 计划校验与目录保持一致

**选择**：`validate_plan` 只有在"上下文工具确实在本轮可用目录里"时，才要求
`requiresTemporalContext` 对应一个上下文步骤。

**原因**：否则模型一旦声明时序需求，它的计划永远无法通过校验（目录里没有那个工具），
三次纠错后任务直接失败——从一个死循环换到另一个死循环。

### D3 · 时序证据判定的触发条件随工具退役自然失效

**选择**：保持 `requires_temporal_context = 计划里是否存在上下文步骤` 的取值方式不变。
工具退役后该条件恒为假，时序分支不再被激活；多条按序排列的日志命中即可满足非时序证据规则。

**备选：把判据改成"同一链路标识下 ≥2 条有序命中才算时序证据"。** 本次不做——判据本身不在
本次范围内，且触发条件修正后已经能达到同样效果。若将来上下文工具重新可用，再单独评估。

### D4 · 提示词显式说明上下文已在检索结果中

**选择**：Planner 的可用工具说明与提示词 MUST 说明"当前链路的日志检索结果本身包含链路顺序信息"，
使它在需要证明前后过程时规划单次检索，而不是去寻找另一个工具。

**原因**：模型之所以反复规划上下文工具，是因为它的信息里"证明时序"只能靠那个工具；
不补上这句，退役只会让它去尝试别的替代工具。

### D5 · 备选方案进文档，不进代码

**选择**：把"用第二次日志检索按链路标识取上下文"写进文档作为备选。

**原因**：当前数据上一次检索已经覆盖整条链路，第二次检索只会重复返回同样的行（实测两个查询
命中完全相同的 4 行）。留作数据源变化时的选项即可，现在实现等于增加一次无收益的调用。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| 退役后彻底失去"日志前后文"能力 | 实测当前链路的日志检索已包含连续多行，能力未真正损失；备选方案已文档化 |
| 退役判定依赖"数据源产不出定位字段"这一事实，数据源变化后可能过时 | 判定依据写进文档并加测试；数据源更换时该判定会被重新审视 |
| 目录与计划校验不一致会导致计划永远非法 | D2 把两者绑定，并加"退役时计划仍合法"的测试 |
| 前端/报告仍可能引用该工具的旧证据 | 历史证据保持只读可查；退役只影响新计划 |

## Migration Plan

1. **无数据迁移**：不改表结构，历史 step 与证据保持可读。
2. **实施顺序**：先补测试（期望新行为失败）→ 加退役标记并让 registry/目录排除 → 调计划校验 →
   补提示词说明 → 调整时序判定触发条件 → 文档化备选方案。
3. **验证**：后端全量 pytest + Ruff + strict Pyright；`openspec validate --all`；`git diff --check`；
   真实 smoke 确认 Planner 不再规划该工具、计划正常通过校验、任务终态与证据状态一致。
4. **回滚**：本变更落在独立 commit，回滚即 revert。

## Open Questions

- `QueryRangeMetric` 因"topic is not metric topic"失败，与本变更是同一类问题（工具正确、数据源
  不满足前置条件）。是否把指标类工具一并退役，需要单独决策——它不影响本变更的规格与任务拆分。
