## Context

动机与实测证据见 `proposal.md`。这里是决定实现方式的现状与依赖关系。

### 现状：一条四方耦合的链

```
工具目录里有 DescribeLogContext / QueryMetric / QueryRangeMetric
        ↓ 前提
validate_plan：声明时序 → 必须且只能有一个上下文步骤；未声明 → 不许有
        ↓ 校验
Planner 提示词：让模型"依赖调用顺序/重试/熔断/恢复时安排上下文步骤"
        ↓ 产出
计划里是否存在上下文步骤
        ↓ 唯一取值来源
requires_temporal_context
        ↓ 唯一消费者
判据：时序档（缺 log_context 且缺「≥2 命中 + 指标」→ 证据不足）
```

**关键事实**：`requires_temporal_context` 在整个仓库里的**唯一消费者**就是那条时序判据。判据一删，这条链上的其余环节就没有任何使用者了。

### 当前判据（`evidence_policy.evaluate_claim_evidence`）

```
① SearchLog 真失败（非空结果）且无命中              → execution_failed
② 无任何 log_hit                                    → insufficient（缺 log_search）
③ 声明时序 且 无 log_context 且 无(≥2命中+指标)      → insufficient（缺 log_context）
④ 未声明时序 且 无指标 且 <2 条命中                  → insufficient（缺 independent_evidence）
⑤ 其余                                             → verified
```

其中③与④都要求当前数据源**永远提供不了**的东西（`log_context`、指标），因此只要模型声明时序需求就必然落到 insufficient——实测在十条告警与单条告警两种输入下完全一致。

### 约束

- 上传方式不改（没有可采集的真实日志文件，采集配置路径不在本仓库可控范围），也不伪造 `PkgId`。
- 报告固定结构与结构校验不变。
- 不改 attempt 上限、退避策略与其它失败分类。

## Goals / Non-Goals

**Goals:**

- 让证据判据只依赖**当前数据源真实能产出的证据**（真实日志命中）。
- 删除"时序"概念，让它在字段、校验、传参、提示词四处一起消失。
- 让 Planner 不再规划注定失败的工具。

**Non-Goals:**

- 不引入新的证据来源，也不补指标主题。
- 不保留"时序结论必须有顺序证据"这道门槛（见 D2 的取舍）。
- 不退役 CLS 告警类与配置类工具。

## Decisions

### D1 · 判据简化三档，以 `log_hit` 为唯一锚点

```
① 必需日志检索真实失败（非空结果）且无命中 → execution_failed
② 无任何 log_hit                          → insufficient
③ 至少一条 log_hit                        → verified
```

**锚点为什么必须是 `log_hit`**：诊断结论的落点是"这台机器上到底发生了什么"，只有日志内容能回答；告警只是输入、知识库只是经验、中间产物只是过程。因此"有没有拿到真实日志命中"是最贴切的充分性判据。

**备选：改成"任一支撑证据（log_hit / log_context / metric）"。** 否掉——那会让"只有指标没有日志"也算充分，而指标在当前数据源不存在；把锚点收紧到 `log_hit` 语义更明确。

**备选：保留"≥2 条命中"的数量门槛。** 否掉——单条真实命中在真实场景里完全可能是充分证据（例如只命中一条明确的异常堆栈）；用数量代替质量为会误伤。

### D2 · 彻底删除"时序"概念

**选择**：删除 `requiresTemporalContext` 输出字段、`validate_plan` 的两条时序规则、runtime 的两处计算与传参、判据的时序档与参数。

**取舍（诚实记录）**：这会失去"时序结论必须有顺序证据"这道门槛。接受它的依据是——

> 在当前数据源上，顺序证据**总是存在**：一次日志检索会返回同一故障链路的连续多行（实测 `incident_id` 查询返回 4 行，覆盖基线→症状→异常→恢复）。
> 也就是说，被删掉的这道门槛在当前数据源上**总会通过**；删它等于去掉形式主义，而不是放宽真实标准。

**备选：把时序证据改成"同一链路下按序号排列的 ≥2 条命中"。** 更严谨，但需要把 Planner 的时序声明**持久化**（`diagnostic_tasks` 加一列，一次 Alembic 迁移），并要求判据解析 `LogJson` 里的链路标识。本次不做，作为将来数据源变化时的候选——如果那时真的需要这道门槛，再单独立项。

### D3 · 退役工具用"数据源可用性"标记，而不是删掉 policy 条目

**选择**：在语义登记表上增加"数据源不满足前置条件"的退役标记（含依据），registry 与模型可见目录同时排除。

**备选：直接把条目从 policy 里删掉。** 否掉——那会退化成"未登记语义"路径（仍可执行、产物落中间产物），与退役意图相反，也丢掉了退役依据。

**备选：只在提示词里叮嘱"别用"。** 否掉——目录里仍存在，模型仍可能规划；且模型看到"调用成功但结果为 0"会产生假阴性结论（CLS 告警类工具就是这种）。

### D4 · Planner 提示词：删指令 + 补事实

**选择**：删掉"依赖调用顺序/重试/熔断/恢复时安排上下文步骤"这条硬性约束，并**新增一条事实说明**：日志检索结果自带链路顺序，需要证明前后过程时直接依据检索结果。

**为什么必须补事实说明**：只删指令会让模型困惑"我需要看前后过程，但没有工具可用"，它可能转而尝试别的替代（例如再排一次日志检索），而"必须且只能有一个日志检索步骤"会把那种计划打回。必须明确告知替代来源在哪里。

### D5 · 改动顺序不可颠倒

```
① 判据（要什么）
② runtime 传参（谁传的）
③ validate_plan（谁校验的）
④ Planner 提示词（谁产生的）
⑤ 工具退役（没用了）
```

**如果先退役工具**：校验与提示词会立刻变成"要求一个不存在的工具"，模型声明的任何合法意图都会让计划被拒，任务直接失败。顺序反了会炸。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| 失去"时序结论需顺序证据"的门槛 | 当前数据源上该门槛总会通过（检索返回整条链路）；替代形态已在 D2 记录为将来候选 |
| 单条命中也算充分，若那条恰好无关，报告可能过度自信 | 报告仍受结构校验与 claims 证据挂链约束；检索本身有查询条件约束 |
| 退役依据依赖"上传 API 不产出包 ID / 账号无指标主题"这两个当前事实 | 依据写进文档并由测试锁住（退役工具不在目录）；数据源变化时该判定会被重新审视 |
| 历史数据里已有 `log_context` 证据 | 证据类型保留，只是不再产生新数据；历史记录仍可读 |
| 删除输出字段会改变 Planner 的结构化输出 schema | 属于本次预期变更；补测试断言计划不再包含该字段 |

## Migration Plan

1. **无数据库迁移**：不改表结构，只改变"写什么"与"判什么"。
2. **顺序**：按 D5 的五步实施，每步同步改测试。
3. **验证**：后端全量 pytest + Ruff + strict Pyright；`openspec validate --all`；`git diff --check`；真实 smoke 核对"计划不再出现上下文工具""单条日志命中即判证据充分""任务终态与信任状态一致"。
4. **回滚**：本变更落在独立 commit，回滚即 revert；无迁移，回滚不需要数据修复。
